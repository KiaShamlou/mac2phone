# Security model — LAN approval preview

All current native, Android and desktop connections use TLS 1.2 with the single ECDHE-PSK-CHACHA20-POLY1305 suite. A cryptographically random 32-byte pre-shared key authenticates possession of the pairing link. ECDHE supplies ephemeral key agreement. Screen, sound and input have no plaintext fallback, HTTP server, WebSocket entry point or active UDP media listener. A separate bounded discovery/request socket exchanges public metadata and ephemeral public keys; private grants in its response are AES-GCM encrypted. Legacy web/UDP helper source remains for reference but is not reachable through the v2 server.

The link's fragment contains the key and, for new approval links, a single-use 60-second grant. It is released only after explicit host acceptance or the host deliberately copying a one-use link; it is not included in Bonjour advertisements, logs or status packets. The system clipboard and any channel used to transfer the link can expose it. Treat it as a password. Apple viewer/native-host pairings use Keychain with device-only accessibility. ReplayKit credentials use an app-group file protected until first unlock and excluded from backup. The iOS copy action expires its local clipboard entry after five minutes. Desktop and Android credentials remain in memory for a session. Stop sharing revokes their session key.

The stream uses **one host-wide TLS key** plus a separate connection grant. An updated production host rejects legacy credentials without a fresh grant. It consumes a grant before changing a client into a media/input-capable state. Approving a nearby request creates one grant; decline, expiry and cancel release none. Host stop/reset disconnects streams and clears grants. This is not persistent device identity, per-device TLS keys, exclusive-controller arbitration or per-viewer revocation UI. The host's screen/input permissions and the viewer's Control toggle still apply.

Bonjour advertisements contain only public device names, platform, protocol version and a random app-instance identifier. They are untrusted hints; never trust a device merely because its name looks familiar. The requester commits to its ephemeral X25519 key and random nonce before seeing the host key, then reveals them. Both derive the response key using HKDF-SHA256 with the complete key/name/platform transcript and display a six-digit comparison code. The host must compare that code with the requesting device before accepting. Commitment/reveal prevents adaptively choosing a key after learning the peer key to grind a matching code. Acceptance transfers the short-lived link using AES-256-GCM with protocol context as authenticated data. This custom pairing protocol still needs independent review; do not represent build/tests as a security audit.

No discovery record contains a PSK or grant. Apple one-use viewer grants stay in memory. ReplayKit grants use individual protected, backup-excluded App Group files with identity and expiration; the extension deletes a grant on consumption. iOS system capture remains user initiated and view-only. Mobile request handling stops on backgrounding (Android may finish a system capture flow already approved in-app). The Watch only controls through its opted-in foreground iPhone.

Media and control share the authenticated stream. Bounds cover control frames, JPEG payloads, audio chunks, client count, message rate, handshake duration, idle sessions and queued media. Disconnects cancel input. The desktop renderer is sandboxed, has no Node integration, receives a narrow context-isolated bridge, denies navigation/popups/unrelated permissions and loads only local resources under a restrictive CSP. Input messages are validated again outside the renderer. Display capture requires an explicit selected-source grant with a short expiry; the bridge exposes only bounded video/audio frames, never arbitrary commands. The Windows helper executes fixed source and receives validated JSON over stdin, without elevation. Linux input spawns fixed `xdotool` arguments without a shell. Android remote input requires both user-enabled Accessibility access and an active control-enabled sharing session. Watch commands are allow-listed and require a connected foreground iPhone with an explicit opt-in; no offline command transfer is used. iOS broadcasts do not expose remote input.

## Known trade-offs and release requirements

- LAN development preview; no security audit or supported stable release yet. Do not expose the listener publicly.
- TLS-over-TCP can stall on loss; low-latency encrypted datagrams/WebRTC need a separate reviewed design, not a return to raw UDP.
- A deliberately shared one-use link grants the host-enabled privileges to whoever redeems it first. Future work: per-device keys, individual session revocation and exclusive-control UI.
- Desktop JPEG uses more bandwidth than hardware video. Clipboard sync, file transfer and held-key gaming input are not implemented.
- Keys shared outside the app, compromised endpoints, hostile local applications, shoulder surfing and denial of service are not addressed by transport encryption.
- Native TLS-PSK ↔ Node and Electron loopback tests cover positive and negative authentication, protocol mismatch and key rotation. Physical-device, multi-client and network-loss testing remains necessary.
- Android MediaProjection/Accessibility and iOS ReplayKit flows require physical permission, lifecycle and resource testing before distribution. Linux Wayland control is not implemented.
- Publish a private security-reporting contact and independently review protocol, storage and Electron packaging before a public release.

Until a private reporting channel exists, avoid posting pairing links, private screen captures or exploit details in public issues. Never attach Keychain exports to bug reports.
